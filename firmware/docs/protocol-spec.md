# 게이트웨이 통신 프로토콜 명세

`vault-gateway/rs485_link.cpp`가 구현체다. 이 문서와 코드가 어긋나면 코드를 기준으로
문서를 고친다(문서 먼저 고치고 코드를 나중에 맞추는 반대 순서 금지 — 실물 보드가
이미 이 스펙으로 동작 중일 수 있으므로).

RS485 보레이트: **19200bps** (`gateway-bridge/.env.example`의 `BAUD_RATE`와 반드시 일치).

## 버스 충돌 최소화 원칙 (2026-09-02 확정)

RS485는 반이중 멀티드롭이라, 여러 게이트웨이가 동시에 선로에 뭔가를 실으면 프레임끼리
겹쳐서 전부 깨진다. 이 프로토콜은 그걸 막으려고 명령을 두 종류로 나눈다.

- **응답 불필요(fire-and-forget)**: LOCK(도어락 정책), RESET(전체/개별 재부팅류). 집중장치가
  보내기만 하면 끝 — 게이트웨이는 아무것도 돌려보내지 않는다. 이 종류는 **브로드캐스트해도
  안전하다**(아무도 응답 안 하니 충돌할 게 없음).
- **응답 필요**: READEROP='R'(리더 스캔). 이건 **반드시 게이트웨이 하나씩, 순차적으로만**
  보내야 한다 — 브로드캐스트로 여러 게이트웨이에 동시에 물어보면 전부 동시에 응답을
  쏟아내서 충돌한다. 펌웨어 쪽에서도 마지막 방어선을 둬서, `READEROP='R'`인데 대상이
  브로드캐스트면 **응답 자체를 만들지 않고 무시**한다(`rs485_link.cpp`의
  `if (readerOp == 'R' && isMine)` — 집중장치 구현 실수로 브로드캐스트+R을 보내도 최소한
  버스가 응답 폭주로 마비되진 않게).
- **게이트웨이는 명령 없이 스스로 아무것도 전송하지 않는다.** 예전엔 도어 상태를 2초마다
  자동으로 하트비트로 쏘고 있었는데, 이게 실제 버그였다 — 버스에 물린 여러 게이트웨이의
  타이머가 서로 안 맞춰져 있어서, 언젠가는 두 게이트웨이의 2초 주기가 겹쳐서 충돌할 수
  있었다(2026-09-02 제거). 지금은 상태(도어 잠금/열림)도 **READEROP='R' 응답 맨 앞에
  한 프레임 얹어서만** 나간다 — 별도 명령이나 자동 타이머 없이, "RFID 데이터를 모을 때
  상태 정보도 한꺼번에 전달"하는 구조.

## 게이트웨이 ID 구조 — 그룹 + DIP주소, 최종 이름은 서버가 부여

게이트웨이가 RS485에서 자기 자신을 밝히는 ID는 **4글자**: `{GATEWAY_GROUP_ID(2글자)}{DIP주소(2자리 HEX)}`.

- **DIP주소**: 74HC165로 읽는 8비트. 같은 RS485 버스(세그먼트) 안에서만 유일 — 버스 레벨
  주소 지정에 필요한 만큼만 담당.
- **GATEWAY_GROUP_ID**: `firmware/vault-gateway/gateway_identity.h`에 정의된 컴파일타임
  상수(설치자가 하드웨어 배치/펌웨어 버전마다 직접 편집 후 빌드). DIP만으로는 "이게 어떤
  하드웨어/펌웨어 배치인지" 알 수 없어서, 서로 다른 배치를 구분하기 위해 붙였다.
- 이 4글자는 **DB의 최종 `gateway_id`(예: `1CORPS-B3-R204-G1`)가 아니다.** 어디까지나
  "이 물리 장치를 가리키는 원시 식별자"다. 사람이 읽을 수 있는 최종 이름은 **서버의
  게이트웨이 등록 화면(`GatewayListPage.jsx`)에서 관리자가 부여**한다 — 지금 이미 있는
  `detected_gateways`(미등록 장치 자동 로그) → 관리자가 방과 매칭 → `gateways`에 정식
  등록되는 흐름을 그대로 재사용한다(새 테이블/화면 필요 없음). 등록되고 나면 **집중장치가
  이 매핑(4글자 원시ID ↔ 최종 gateway_id)을 캐시해서 관리** — 이후 서버로 보고할 땐 최종
  이름으로 보낸다.
- `"FF"`는 브로드캐스트 예약값이라 GATEWAY_GROUP_ID로 쓰면 안 된다 — `gateway_identity.h`의
  static_assert가 이 값이면 컴파일 자체를 막는다(대문자 "FF"만 검사).

## RFID는 "이벤트"가 아니라 "지금 상태 조회"다

스마트폰이 슬롯에 몇 시간씩 계속 거치돼 있는 걸 실시간으로 파악해야 하는 시스템이라,
"새로 인식된 순간에만 보고"하는 방식은 안 맞는다(거치돼 있는 카드는 MFRC522의
`PICC_IsNewCardPresent()`가 REQA 기반이라 한 번 읽고 나면 HALT 상태가 돼서 계속
거치돼 있어도, 심지어 빼도 다시 안 잡힌다). 그래서:

- 게이트웨이는 리더를 스스로 훑지 않는다 — **집중장치가 `READEROP='R'`로 명시적으로
  물어볼 때만** 리더를 재초기화해서 다시 감지 가능하게 만든 뒤 응답한다.
- 응답은 "카드가 새로 인식됨" 이벤트가 아니라 "지금 이 순간 이 리더에 뭐가 있는지"
  현재 상태(`PRESENT` 0/1 + UID)다.
- **check_in/check_out(입고/출고) 전환 판단은 게이트웨이가 하지 않는다.** 게이트웨이는
  매번 있는 그대로의 현재 상태만 보내고, 이전 상태와 비교해서 "새로 놓임"/"빠짐" 전환을
  만드는 건 **집중장치(`gateway-bridge`)가 기본으로 담당**하며, 그 결과를 서버 이벤트
  관리(`backend/src/services/ingestService.js`)로 넘겨서 확장 가능한 구조로 간다 —
  즉 집중장치가 리더별 마지막 상태를 들고 있다가, 새 응답이 오면 diff해서
  `check_in`/`check_out`/`unknown`을 만들어 `POST /api/ingest/events`로 보낸다.

## 명령 (집중장치 → 게이트웨이)

고정 11바이트 + 개행(`\n`):

```
!{ID}{LOCK}{RESET}{READEROP}{READERIDX}{CHECKSUM}
```

| 위치 | 이름 | 길이 | 허용값 | 의미 |
|---|---|---|---|---|
| 0 | 시작 | 1 | `!` | 프레임 시작 |
| 1-4 | ID | 4 | `{GATEWAY_GROUP_ID 2글자}{DIP 2자리 HEX}` | 대상 게이트웨이(위 "게이트웨이 ID 구조" 참고). `FFFF`=전체 브로드캐스트 |
| 5 | LOCK | 1 | `O`/`C` | Open/Close — 서버가 판단한 "지금 잠금/열림" 정책 상태. 게이트웨이는 이 값을 그대로 캐시했다가 OPEN_BTN 입력과 대조한다(주간 스케줄 자체는 서버가 계산, 게이트웨이는 안 들고 있음) |
| 6 | RESET | 1 | `A`/`I` | 전체/개별 재부팅류 — **TODO: 아직 firmware에서 미구현**, 파싱만 하고 무시 |
| 7 | READEROP | 1 | `R`/`A` | `R`=지금 리더 스캔해서 상태 보고, `A`=응답 불필요(락 상태만 캐시) |
| 8 | READERIDX | 1 | `0`-`9`/`A` | READEROP='R'일 때만 의미 있음 — `0`-`9`면 그 리더 하나만, `A`면 10개 전부 순서대로 스캔+응답 |
| 9-10 | CHECKSUM | 2 | HEX | `!`부터 READERIDX까지(인덱스 0~8, 9바이트) XOR |

체크섬이 안 맞거나 프레임 길이가 11바이트가 아니면 게이트웨이는 조용히 버린다(재전송은
집중장치 책임 — 응답 없음을 재전송 트리거로 씀).

## 응답 (게이트웨이 → 집중장치)

**응답은 오직 `READEROP='R'`이고 자기 앞으로(브로드캐스트 아님) 온 명령에 대해서만
나간다.** 그 외 상황(LOCK/RESET만 온 경우, 자기 프레임이 아닌 경우, 체크섬 불일치)엔
아무것도 전송하지 않는다 — 위 "버스 충돌 최소화 원칙" 참고.

한 번의 `R` 명령에 대해 응답은 항상 이 순서로 나간다:

1. **상태 프레임 1개** (그 시점의 실제 도어 상태 + 게이트웨이가 인식 중인 정책)
   ```
   :ID:{4글자}:LOCK:{O|C}:POLICY:{O|C}:END:{CHECKSUM 2 hex}
   ```
   - `LOCK`: **LOCK_STATE 핀으로 실측한 실제 도어 상태**
   - `POLICY`: 서버가 마지막으로 내려준 LOCK 명령을 게이트웨이가 캐시해서 "지금 이렇게
     적용해야 한다"고 인식하고 있는 값(`door_lock.cpp`의 `doorLock_isCommandedUnlocked`)
   - 이 둘은 다를 수 있다 — 예: 정책은 열림 허용(`POLICY=O`)인데 아직 아무도 버튼을 안
     눌러서 실제로는 잠긴 채(`LOCK=C`)인 경우. 집중장치가 "게이트웨이가 지금 뭘 인식하고
     있는지"와 "실제로 어떤 상태인지"를 구분해서 볼 수 있게 둘 다 실었다(2026-09-02).
2. **리더 상태 프레임 1개 또는 10개** (READERIDX가 `0`-`9`면 1개, `A`면 리더 0부터 9까지
   순서대로 10개)
   ```
   :ID:{4글자}:RD:{리더idx 1 hex}:PRESENT:{0|1}:UID:{UID hex, present=0이면 빈 문자열}:END:{CHECKSUM 2 hex}
   ```

즉 집중장치는 `R` 명령 하나를 보내면 **정확히 (1 + 요청한 리더 수)개**의 응답 프레임이
올 것을 기대하면 된다 — 이 개수만큼 받으면 그 게이트웨이 차례는 끝난 것으로 보고 바로
다음 게이트웨이로 넘어가도 된다(고정 딜레이로 기다릴 필요 없음). 프레임 하나에 다 몰아
넣지 않고 여러 개로 쪼갠 이유는, 응답 하나가 너무 길어져서 그 시간 동안 게이트웨이의
`loop()`가 오래 묶이는 걸 피하기 위해서다.

두 응답 다 체크섬은 `:ID:`부터 마지막 `:`까지 전체 XOR.

## 폴링 주기 / 명령 간격 (집중장치 설계 시 참고 — 실측 전 추정치)

**아직 실물 보드로 측정한 값이 아니다** — 실측 전까지는 아래를 출발점으로 삼고,
하드웨어 붙는 대로 재보정할 것.

19200bps ≈ 바이트당 약 0.52ms(8N1 가정)로 계산하면:

| 항목 | 길이 | 대략 전송 시간 |
|---|---|---|
| 명령 프레임 | 12바이트(개행 포함) | ~6ms |
| 상태 응답 프레임 | 24바이트 | ~13ms |
| 리더 상태 프레임(UID 없을 때/있을 때) | 34~56바이트 | ~18~29ms |

여기에 리더 1개당 실제 스캔 시간(`PCD_Init()` + 카드 감지 시도, 아직 벤치 미측정 —
MFRC522 특성상 각 수 ms 단위로 추정)을 더해야 한다. 리더 10개 전부(`READERIDX='A'`)
요청하면 전송+스캔 합쳐서 **게이트웨이 한 대당 대략 수백 ms** 걸릴 것으로 추정 — 세그먼트
하나에 게이트웨이가 최대 20대까지 물릴 수 있다는 `docs/architecture.md` 기준을 그대로
적용하면, **버스 전체를 한 바퀴 도는 데 수 초가 걸릴 수 있다.**

이걸 줄이는 현실적인 방법 하나: **문이 닫혀 있는 게이트웨이는 리더 상태가 바뀔 수가
없다**(슬롯에 손이 안 닿으니까). 집중장치가 각 게이트웨이의 마지막 상태 프레임으로
"지금 문이 열려 있는지"를 이미 알고 있으므로, **닫혀 있는 게이트웨이는 리더 전체
스캔(`READERIDX='A'`) 대신 어쩌다 한 번만 확인하고, 열려 있는 게이트웨이 위주로 자주
폴링**하는 식으로 버스 대역폭을 열려 있는(=지금 사람이 조작 중인) 곳에 몰아줄 수 있다.
이건 집중장치(`gateway-bridge`) 쪽 스케줄링 로직 설계 시 반영할 사항이라 지금 펌웨어
쪽에서 할 일은 없다.

## Fail-secure (통신 두절 대응)

마지막으로 유효한 LOCK 명령을 받은 지 `COMMS_TIMEOUT_MS`(현재 5000ms, `door_lock.h`)가
지나면 게이트웨이는 서버 명령과 무관하게 **무조건 잠금 상태로 전환하고 로컬 OPEN_BTN도
무시**한다. 행정반에 별도 비상 물리키가 있다는 전제로 확정(2026-09-01) — 통신 장애 시
현장 편의보다 보안(정보 유출/도난 방지)을 우선한다.

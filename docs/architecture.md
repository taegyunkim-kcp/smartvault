# NFC Smart Vault — 협업 가능한 구조로 재설계 제안서

> 목적: 기존 1인 개발 코드(`data.zip`, `.ino`)는 **참고용**입니다. 여기서는 그 코드를 고치는 게 아니라,
> 그 안에 들어있는 "검증된 로직"만 뽑아내고, 확장·협업이 가능한 형태로 **새로 설계**합니다.

---

## 1. 기존 코드에서 확인된 사실 (설계 근거)

새로 설계하기 전에, 기존 코드가 실제로 어떻게 동작하고 있었는지부터 정리했습니다. 이건 "무엇을 유지해야 하는 핵심 로직"과 "무엇을 반드시 버려야 하는 구조"를 가르는 기준이 됩니다.

### 1-1. 하드웨어/펌웨어 (`ver1_2_1_..._MCU.ino`)
- Arduino 기반 MCU 1개가 **MFRC522 RFID 리더 최대 10개**를 SPI SS핀 멀티플렉싱으로 제어
- 게이트웨이마다 `myName`(g1, g2...) 이라는 고유 ID를 가지고, `SoftwareSerial`로 **RS485 데이지체인**을 통해 상위 시스템(Python)과 통신
- 통신 프로토콜이 `!g1CCCO`, `:ID:...:RD:...:END:` 같은 **직접 정의한 텍스트 프로토콜** — 구분자 파싱을 직접 처리, 체크섬/재전송 없음
- 워치독 타이머(`wdt`), 도어 상태 핀, 부저 멜로디, 리더 초기화 로직까지 — **현장에서 실제로 튜닝된 로직**이라 이 부분의 타이밍/상태값은 그대로 자산으로 유지해야 함

### 1-2. 게이트웨이 브리지 (`serial-org-loop.py` 등)
- 초 단위(`readTimeList`)로 폴링하며 시리얼 포트에 명령 전송 → 응답을 파싱해서 **로컬 텍스트 파일**(`log/*.txt`, `secData/company*/room*/*.txt`)에 기록
- 파일 하나(`sum.txt`)가 **1GB 이상**까지 누적되는 구조 — DB가 아니라 파일 append 방식
- 스크립트 버전이 `15Data30.py`, `15Data30 extend.py`, `...backup.py`, `...Debug.py` 등 **파일명으로 버전 관리** 중 (git 미사용 추정)

### 1-3. 백엔드 (`server.js`, Express + MySQL)
- **DB 접속 정보(호스트/계정/비밀번호)가 소스코드에 평문으로 하드코딩**되어 있고, 주석 처리된 중복 버전도 함께 커밋되어 있음 → 이건 재설계 여부와 무관하게 **지금 바로 로테이션(비밀번호 변경) 권장**
- SQL 쿼리를 문자열 concat으로 직접 조립(`"UPDATE ... WHERE (IDsequence = '" + idxcode + "')"`) → SQL Injection에 열려있음
- `cors({ origin: '*', credentials: true })` — 이 조합은 스펙상 브라우저에서 정상 동작하지 않거나 보안상 위험한 설정
- 라우트 핸들러 하나가 여러 단계 조건 분기(`Searchoption1===1 && Searchoption2===6` 등)를 안에서 다 처리 — 비즈니스 로직/DB 접근/응답 포맷팅이 분리되어 있지 않음

### 1-4. 프론트엔드 (React, CRA + react-app-rewired)
- 라우팅 구조 자체(`/regi/newUser`, `/regi/newDetected`, `/regi/SetupTimeTable` 등)는 **등록 플로우가 명확하게 나뉘어 있어 재사용 가치가 있음**
- 다만 `Menu.jsx`/`Menucopy.jsx`, `MainFrame.jsx`/`MainFrame-back.jsx`, `TableCreate.jsx`/`TableCreate1.jsx`처럼 **"copy/back" 파일이 진짜 버전과 나란히 존재** — 협업 시 "어느 게 최신인지" 판단 불가능한 상태

**결론**: 로직(RFID 멀티리더 제어, RS485 주소체계, 등록 플로우, 도어 상태 판단)은 실전 검증된 자산이지만, **구조(버전관리, 보안, 계층 분리, 데이터 저장방식)는 처음부터 다시 짜는 게 맞습니다.** 사장님 판단이 정확합니다.

## 2. 새 아키텍처 개요

부대 1개 = 내무반 10~수십 개 = Vault(보관함) 10~수십 대 = RFID 리더 최대 수백 개, 이걸 **부대 안의 중앙관리서버 1대**가 모니터링해야 하고, **인터넷이 없는 폐쇄망**이라는 전제가 붙었습니다. 이 조건이 아키텍처의 핵심 제약이라 다이어그램을 계층형으로 다시 그렸습니다.

```
[내무반 1]  Vault(MCU+RFID×10) ─┐
[내무반 2]  Vault(MCU+RFID×10) ─┤  RS485 buses
[내무반 3]  Vault(MCU+RFID×10) ─┤  (건물/층별로 분리)
   ...                          │
[내무반 N]  Vault(MCU+RFID×10) ─┘
                │
                ▼
     ┌─────────────────────┐
     │  건물별 Concentrator  │  ← RS485 세그먼트 종단, Python 브리지 상주
     │  (미니PC/산업용 게이트웨이)│    로컬 SQLite 버퍼(오프라인 큐)
     └──────────┬───────────┘
                │ 부대 내부망(유선 LAN, 인터넷 미경유)
                ▼
     ┌─────────────────────┐
     │  중앙 관리서버 (부대 내)│  ← 인터넷 연결 없음, 전부 자체 호스팅
     │  API Server + DB      │
     │  + 관리자 대시보드      │
     └─────────────────────┘
```

핵심 설계 포인트 4가지:
1. **RS485 세그먼트 분할**: RS485 한 버스에 물릴 수 있는 노드 수(표준 트랜시버 기준 32개)와 배선 길이 한계 때문에, 내무반이 많은 부대는 **건물/층 단위로 RS485 버스를 나누고**, 그 버스마다 Concentrator(로컬 브리지 PC) 1대를 둡니다. 지금처럼 브리지 하나가 시리얼 포트 하나만 보는 구조로는 내무반 수십 개를 감당할 수 없습니다.
2. **오프라인 내성**: 폐쇄망이라도 부대 내부 LAN 자체가 순간적으로 끊길 수 있습니다. Concentrator는 중앙서버와 연결이 끊겨도 로컬(SQLite)에 이벤트를 쌓아두고, 재연결되면 밀린 데이터를 동기화합니다. **잠금/해제 판단 자체는 MCU/Concentrator 레벨에서 독립적으로 동작**해야 하고, 중앙서버는 "기록·모니터링·정책 배포" 역할로 한정합니다 — 중앙서버가 죽어도 현장 보관함은 정상 동작해야 합니다.
3. **파일 기반 로그 → DB 직접 적재**: Concentrator가 텍스트 파일에 append 하는 대신, 구조화된 이벤트를 중앙 API로 바로 전송(또는 오프라인 시 로컬 큐 후 재전송)
4. **비밀정보 분리 + 완전 자체 호스팅**: 인터넷 의존 서비스(클라우드 DB, 외부 NTP, 외부 시크릿 매니저 등) 전부 제거하고 부대 내부에서 자체적으로 돌아가는 구성만 사용

## 3. 다중 사이트 · 폐쇄망 환경 대응 설계

### 3-1. 계층적 ID 체계로 전환

지금은 `myName`이 `g1`, `g2`처럼 평면적인 이름입니다. 부대 하나에 내무반 수십 개, 나중에 부대 여러 곳으로 확장되는 걸 감안하면 처음부터 계층 ID를 써야 나중에 안 꼬입니다.

```
{부대코드}-{건물코드}-{내무반코드}-{게이트웨이순번}
예: 1CORPS-B3-R204-G1
```

- 이 ID를 MCU 펌웨어의 `myName` 자리에 그대로 넣고, DB의 `gateways` 테이블 기본키로도 사용
- 나중에 부대가 여러 곳으로 늘어나도(사업계획서상 확장 시나리오) 이 체계 그대로 확장 가능

### 3-2. RS485 세그먼트 설계 기준

| 항목 | 기준 | 비고 |
|---|---|---|
| 세그먼트당 최대 노드 수 | 표준 트랜시버 기준 32개, 여유 두고 20개 이하로 운영 권장 | 내무반 20개 이상인 건물은 세그먼트 2개 이상으로 분리 |
| 배선 길이 | 한 세그먼트 내 배선이 길어지면 종단저항·통신 안정성 확인 필요 | 건물 단위 분리가 현실적 |
| Concentrator 1대당 담당 범위 | 세그먼트 1~2개 (내무반 약 15~30개) | Concentrator는 저사양 미니PC/산업용 PC로 충분 |

부대 규모(내무반 10개 ~ 수십 개)를 감안하면, **건물별로 Concentrator를 1대씩 두고, 중앙서버는 Concentrator들의 접속만 받는 구조**가 가장 현실적입니다. 내무반 10개짜리 소규모 부대는 Concentrator와 중앙서버를 물리적으로 한 대(PC 한 대)에 합쳐도 됩니다 — 규모에 따라 스케일업/스케일다운이 가능하게 설계합니다.

### 3-3. 폐쇄망 특화 고려사항

| 항목 | 일반 인터넷 환경 가정 | 폐쇄망(부대) 대응 |
|---|---|---|
| 시간 동기화(NTP) | 공용 NTP 서버 | 중앙서버를 부대 내부 NTP 소스로 지정, 모든 Concentrator/클라이언트가 이걸 참조 |
| 소프트웨어 업데이트 | `git pull`, `npm install`, OTA | 인터넷 미경유 — 검증된 패키지를 USB 등 물리 매체로 반입하는 내부 배포 절차 필요 (군 보안 규정에 따른 반입 승인 절차 포함) |
| DB/시크릿 관리 | 클라우드 매니지드 DB, AWS Secrets Manager 등 | 전부 온프레미스: PostgreSQL/MySQL 자체 호스팅, `.env` 또는 로컬 Vault(HashiCorp Vault 자체 구축)로 제한 |
| 원격 장애 대응 | 원격 로그 수집(Sentry 등 외부 SaaS) | 로컬 로그 수집(자체 ELK 또는 파일 로그 + 로테이션)만 사용, 외부 전송 없음 |
| 도메인/인증서 | 공인 도메인 + Let's Encrypt | 내부 CA 발급 인증서 또는 사설 IP 기반, 공인 인증서 발급 불가 전제 |

### 3-4. 감사(Audit) 로그 강화

민간 상용 사물함과 달리, **군부대 스마트폰 보관함은 "누가 언제 폰을 넣고 뺐는지"가 지휘/보안 감사 목적**과 직결됩니다. 데이터 계층 설계 시 아래를 기본으로 포함합니다.

- `rfid_events` 테이블: (부대ID, 내무반ID, 게이트웨이ID, 리더인덱스, RFID UID, 이벤트유형(입고/출고), 타임스탬프) — **수정·삭제 불가(append-only)**, 삭제는 보존기간 정책에 따른 별도 아카이빙만 허용
- 도어 개폐 이벤트도 별도 테이블로 기록 (누가 강제로 열었는지 등 이상 상황 추적)
- 관리자 계정의 조회/설정 변경 이력도 감사로그 테이블에 별도 기록

### 3-5. 중앙서버가 다중 Concentrator를 수용하는 방식

부대 하나에서 Concentrator가 최대 수 대~십수 대가 동시에 중앙서버로 이벤트를 보냅니다. 인터넷 트래픽이 아니라 폐쇄망 내부 트래픽이라 규모 자체는 크지 않지만, 설계는 아래처럼 갑니다.

- 중앙서버는 Concentrator별 **persistent 연결(WebSocket 또는 장기 TCP)** 을 유지해 실시간성 확보 + 연결 끊김 자체를 장애 감지 신호로 활용(대시보드에 "내무반 204 연결 끊김" 알림)
- 이벤트 수신은 큐(내부 메시지 큐, 예: Redis Streams — 이것도 로컬 설치) 뒤에서 비동기로 DB에 적재해 순간 부하 흡수
- DB는 부대/건물/내무반 기준으로 인덱스 설계, 대시보드 조회는 "부대 전체 → 건물별 → 내무반별" 드릴다운 구조로 쿼리 최적화

## 5. 통신 프로토콜 재설계

현재 프로토콜(`!g1CCCO`, `:ID:...:RD:...:END:`)은 동작은 하지만, 팀원이 늘면 "이 5번째 글자가 뭘 의미하는지" 코드를 읽어야만 압니다. 재설계 시:

1. **명세서를 코드보다 먼저 작성** (`firmware/docs/protocol-spec.md`)
   - 명령어 표: `!{게이트웨이ID}{잠금상태}{리셋}{리더동작}{기타}` 형태로 필드별 의미/허용값을 표로 정리
   - 응답 형태(`:ID:`, `:RD:`, `:END:` 등 delimiter)도 동일하게 표로 정리
2. **경량 프레이밍 유지, 체크섬만 추가**: RS485 대역폭이 크지 않으므로 JSON 전면 전환보다는, 기존 텍스트 프로토콜에 **XOR 체크섬 1바이트**만 추가해 전송 오류를 잡아내는 정도가 현실적입니다 (완전 JSON은 저사양 MCU에 부담)
3. **Python 브리지에서 파싱 직후 구조화**: 브리지 안에서 파싱한 결과는 즉시 아래 형태의 이벤트로 변환해서 API로 전달

```json
{
  "gateway_id": "g1",
  "event_type": "rfid_detected",
  "reader_index": 3,
  "rfid_uid": "3A9F1C22",
  "door_state": "closed",
  "ts": "2026-08-24T10:15:03Z"
}
```

이렇게 하면 백엔드/DB/프론트는 저수준 텍스트 프로토콜을 몰라도 되고, 펌웨어 담당자만 그 명세서를 알면 됩니다 — **역할 분리가 곧 협업 가능 구조**입니다.

## 6. 데이터 계층 재설계

| 현재 | 문제 | 제안 |
|---|---|---|
| `log/*.txt`, `secData/.../total.txt` (append, 최대 1GB+) | 파일 잠금 경쟁, 조회 불가능한 raw text, 백업/복구 어려움 | RDB의 `events`, `rfid_reads`, `door_states` 테이블로 즉시 적재 |
| `server.js` 안에 SQL 문자열 concat | SQL Injection | ORM 또는 파라미터 바인딩 쿼리(`?` 플레이스홀더) 강제, repository 계층에서만 SQL 작성 |
| 코드에 평문 비밀번호 | 유출 시 DB 전체 노출 | `.env` + 배포 환경에서는 시크릿 매니저(AWS Secrets Manager, 또는 최소 `.env` + `.gitignore`) |
| 세션/인증 로직이 라우트 안에 산재 | 재사용 불가 | `middlewares/auth.js`로 통합, JWT 또는 세션 방식 택1 |

**즉시 조치 권장(재설계와 별개로 지금 해야 할 것)**: 기존 서버가 아직 살아있다면 DB 비밀번호부터 교체하세요. 코드가 zip으로 공유된 이상 이미 노출된 것으로 간주하는 게 안전합니다.

인원(군인)-RFID 매핑, 도어 개폐 정책, 판정 이벤트까지 포함한 상세 스키마는 [data-model-personnel-door-control.md](./data-model-personnel-door-control.md) 참고.

## 7. 협업 프로세스 (개발자 합류 대비)

사업계획서에 소프트웨어 개발자 합류 예정(’26.6)이 명시돼 있으니, 그 시점 기준으로 준비하면 됩니다.

1. **Git 브랜치 전략**: `main`(배포) / `develop`(통합) / `feature/*` — 팀 2~3명 규모에는 GitHub Flow(단순히 `main` + `feature/*` + PR)가 오히려 더 적합할 수 있습니다
2. **"copy/back" 파일 금지**: 버전은 git 커밋/브랜치로만 관리 — `MainFrame-back.jsx` 같은 파일이 다시 생기지 않도록 `.gitignore` + PR 리뷰 규칙에 명시
3. **환경변수 템플릿**: `.env.example`을 레포에 커밋하고 실제 `.env`는 절대 커밋 금지
4. **온보딩 문서**: `docs/onboarding.md`에 "로컬에서 백엔드+DB+브리지 띄우는 법"을 `docker-compose up` 한 줄로 끝나게 정리 — 신규 개발자가 첫날 바로 개발 가능하게
5. **API 명세**: Swagger/OpenAPI로 프론트-백엔드 계약을 문서화하면, 프론트 개발자가 백엔드 코드를 안 봐도 작업 가능

## 8. 단계별 로드맵 제안

| 단계 | 내용 |
|---|---|
| Phase 0 | 기존 서버 DB 비밀번호 교체, 레포 구조 세팅, `.env` 분리 |
| Phase 1 | 프로토콜 명세서 작성(체크섬 포함) → 펌웨어 리팩토링(로직은 유지, 파일 구조만 정리), 계층형 ID 체계 확정 |
| Phase 2 | Concentrator(구 게이트웨이 브리지) 재작성 — 로컬 큐잉/오프라인 재동기화 포함, RS485 다중 세그먼트 대응 |
| Phase 3 | 백엔드 API 재작성 (레이어 분리, SQL 파라미터 바인딩, 인증 미들웨어, 다중 Concentrator 수용 구조) |
| Phase 4 | 프론트엔드 정리 (부대→건물→내무반 드릴다운 대시보드, 기존 라우팅 구조 재사용) |
| Phase 5 | 소규모 시범 배치(내무반 1~2개)로 실증 → 문제점 보완 |
| Phase 6 | 폐쇄망 배포 절차 확정(오프라인 설치 매뉴얼, 내부 CA/인증서, 로컬 NTP) 및 CI/CD, 온보딩 문서 정비 → 팀원 합류·부대 확대 배치 준비 완료 |
